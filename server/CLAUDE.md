# server/: routes, API clients and the cache

External APIs (Blizzard, Raider.IO, Warcraft Logs, Raidbots) are called from here, never from the browser. That avoids CORS, keeps the credentials server-side, and lets every response be cached. Pages consume the routes with `useFetch` and import the route's exported response type (e.g. `RosterMember`) for end-to-end typing.

## Files

- `server/api/roster.get.ts`: thin route over `fetchRoster()` in `server/utils/rosterData.ts`, which fetches the guild roster from Raider.IO and caches it an hour. A cached function so the raid lists can use the roster to tell a guild night from a pug. The transform lives in `server/utils/roster.ts`
- `server/utils/roster.ts`: owns `RaiderIoMember`, `RosterMember` and `toRosterMembers()`, the pure filter-map-sort applied to Raider.IO's response. Rank `99` is not a guild rank but Raider.IO's sentinel for a character it could not place, and `toRosterMembers()` filters those out so they never reach the page or the member count. Separate from the route so it can be tested without a Nitro runtime, since a route module runs its handler definition the moment it is imported. Also `rosterKey()`, which matches name and realm however an API spells them
- `server/utils/optOut.ts`: the opt-out list and the name matching around it. One list, applied wherever a character is named, so removing someone is a single edit and a deploy rather than a hunt through routes (then the `CACHE` KV keys are deleted by hand, see "Blizzard API terms" in the root CLAUDE.md). Matching is case-insensitive and lives in `isNameIn()`, separate from the list, so it can be tested without a real person being in it. Applied in `toRosterMembers()`, `toMemberIndex()` and, through `withoutOptedOut()`, on the raid detail route
- `server/utils/blizzard.ts`: the Blizzard API client. OAuth client credentials against `oauth.battle.net` through the `oauth4webapi` library (Blizzard strongly recommends a stable library over a hand-written OAuth flow; it is built on fetch, so it runs on Workers), token held in module scope and renewed a minute before its 24 hours run out, one retry on a 401. `blizzardGet(path, namespace)` calls `eu.api.blizzard.com` in `en_GB` with a `profile-eu`, `static-eu` or `dynamic-eu` namespace, returns null for a 404 and throws on anything else, a 429 included. Missing credentials throw a 503 with `BLIZZARD_NOT_CONFIGURED`; `isBlizzardNotConfigured()` tells that apart from an outage
- `server/utils/warcraftlogs.ts`: the Warcraft Logs v2 client. Holds the OAuth token in module scope, runs one GraphQL query per call, and throws a 503 when the credentials are missing so a page can say "not configured" instead of "down" (`isNotConfigured()` tells that apart from an outage). Every query also asks for `rateLimitData`, and the last reading of the client's hourly points (3600, account-wide) guards the next call: `wclQuery(query, vars, 'low')` is refused at 80% of the hour, the default `'high'` at 95%. Low is for extras (character parses, the loggers' scan); a refused or failed part makes a result incomplete, and incomplete results are kept only `INCOMPLETE_MAX_AGE_MS` (10 minutes). Every outbound call, Blizzard's included, has a `UPSTREAM_TIMEOUT_MS` timeout. Also owns `GUILD`, the difficulty-integer map (an unmapped value returns null and the UI drops the badge rather than inventing a name), `RAID_TIERS` (the guild's raid tiers as Warcraft Logs zone ids, newest first; the first is the default everywhere and adding a tier is one line) and `GUILD_LOGGERS`, the Warcraft Logs user ids of the people who log guild raids. Until late 2024 guild logs were uploaded as personal logs with no guild set, so every Dragonflight tier and Nerub-ar Palace only exist through them
- `server/utils/raidNights.ts`, `server/utils/raidDetail.ts`: `fetchRaidNights(tierId)` (every guild night in one tier: guild-tagged logs with at least 5 current roster members in their boss fights, plus the loggers' personal logs with at most 30 players and at least 8 roster members, which keeps pugs, solo runs and LFR out. Only Normal, Heroic and Mythic encounters count (`isGuildRaidDifficulty()`), so LFR and Mythic+ runs in a raid log are ignored; the current tier is cached an hour, a finished tier a week, since one costs about 130 API points) and `fetchRaid(code)`, the Warcraft Logs fetches behind the raid pages, as cached functions refreshed once an hour. In `server/utils` rather than in the routes so the character pages can reuse them. `server/utils/raids.ts` holds the pure `collapseFights()` (one row per boss and difficulty on a raid night page) and `groupRaidNights()`: logs that overlap (two raiders logging at once) or follow within three hours (a night uploaded in parts) are one night, counted across all its logs and linking to the most complete one
- `server/api/raids.get.ts`, `server/api/raids/[code].get.ts`: the two raid routes, thin wrappers that call the fetchers and re-export their types; the detail route applies opt-outs after the cache. On raid night pages, players off the roster (pugs and former members alike, the site cannot tell them apart) are plain text in a dimmed class colour, with no label
- `server/api/characters/[realm]/[name].get.ts`: one character on the current guild roster, and only them: anyone else, a pug from a raid log say, gets the same 404 as an unknown name, and so does an opted-out one. Combines Raider.IO (gear, Mythic+, raid progression, portrait), Warcraft Logs rankings for one tier (`?tier=<zone id>`, all three difficulties in one aliased query, `hps` for healers), the guild raid nights the character was in, and Blizzard's `character-media` for the full-body render (cached an hour per character on its own). Each part is soft: one that fails leaves the page without it and marks the result incomplete; missing credentials for either API do not count as a failure. The whole profile is cached 5 hours per character and tier
- `server/api/render/[...path].get.ts`: serves a character render fetched from `render.worldofwarcraft.com`, because Blizzard's image server sends no cache header and the PNG is about 500 KB; `routeRules` in `nuxt.config.ts` gives it a one-day `cache-control`. Only paths matching `isRenderPath()` are fetched, so the route cannot be used to fetch anything else
- `server/utils/character.ts`: the character page's pure transforms (`toDifficultyRankings()`, `toGear()`, `findRaidNights()`, `toRenderUrl()` and friends), kept out of the route for testing
- `server/utils/upgradeTracks.ts`: turns Raidbots' static bonus id table (`raidbots.com/static/data/live/bonuses.json`) into a bonus-id-to-track lookup, so each gear piece can show "Hero 4/6". Neither Raider.IO nor Warcraft Logs names the track. The character route fetches the table server-side and caches only the small lookup, for a day; if Raidbots is down the gear shows without tracks

## Caching

Every cached function uses `defineCache` (`server/utils/cache.ts`), not Nitro's `defineCachedFunction`: Nitro's shares one in-flight promise per key across requests and refreshes stale entries in the background, and on Cloudflare a dropped background task or cancelled request left that promise unsettled, hanging every later request for the key (it took production down once KV made entries arrive stale). `defineCache` reads, returns an entry that is only past its `maxAge` at once and refreshes it after the response through `event.waitUntil` (one refresh per key per instance, never awaited by another request), loads inside the request when nothing is stored or the entry fails `validate`, serves the old value if a load fails, and versions entries by the loader's source (plus `dependsOn`) so a new deploy never reads an old shape from KV. A background refresh still running after 25 seconds (Cloudflare cuts `waitUntil` off at about 30) is given up, and the next request for that key loads inline. Only the outermost call serves stale: `load` gets a stand-in event, and a cached function called with it loads inline, so a parent entry is never stored as fresh with a stale part. That is why every cached function takes the request's `event` first: pass the `event` a loader receives on to any cached function it calls.

No entry is ever older than `RETENTION_LIMIT_MS`, 30 days: past it, `readThrough` deletes the entry and never serves it, not even as the fallback when a load fails. The Blizzard Developer API Terms of Use allow data from their API to be kept 30 days at most, and Raider.IO and Warcraft Logs data is built from it, so the limit holds for every cache.

In production the cache is mounted on `memoryOverKv` (`server/utils/cacheDriver.ts`, mounted by `server/plugins/cacheStorage.ts`): each instance's memory, backed by the Workers KV namespace bound to the Pages project as `CACHE`. KV is shared by every Cloudflare instance and survives deploys, which is what keeps the Warcraft Logs budget down; without the binding it is plain per-instance memory. KV entries expire on their own after `KV_TTL_SECONDS` (8 days). An instance trusts its own memory copy of a shared entry for a minute (`KV_RECHECK_MS`), then looks at KV again and takes KV's copy if its `mtime` is newer, so a warm instance does not refresh from Warcraft Logs what another instance already has. A KV error is logged and never fails a request. Dev keeps Nuxt's file cache in `.nuxt/cache`. Only the Warcraft Logs caches (`raids`, `raids-past`, `raid`, `character`) and the news list (`news-list`, so a new instance does not ask D1 during the landing page's render, keyed by the build id so a deploy or preview never serves another build's list; not `news-post`, whose key comes from the URL, so any made-up slug would spend a write) go to KV, see `SHARED_CACHES`: its free tier allows 1000 writes a day, one per cache refresh, and Raider.IO and Blizzard data is cheap to fetch again, so it stays in memory. Only production builds write to KV (`runtimeConfig.cacheKvWrites`, set from `CF_PAGES_BRANCH === 'main'` at build time); previews and local builds read the shared cache but never write. On the free plan, going over the limit costs nothing: KV refuses writes for the rest of the day and the cache falls back to memory.

`.github/workflows/warm-raids-cache.yml` pings `/api/raids` so the current tier's list is refreshed by a cron rather than a visitor. It is scheduled every 15 minutes, but GitHub delays scheduled runs on a quiet repository and in practice it runs every six to seven hours. Nothing else is warmed.

Workers on Cloudflare's free plan allow 50 outbound requests per incoming request, which rules out one Blizzard call per guild member in a single load (see #149).

## Environment variables

The OAuth credentials for Warcraft Logs and Blizzard are server-only `runtimeConfig` in `nuxt.config.ts` (`wcl.clientId`, `wcl.clientSecret`, `blizzard.clientId`, `blizzard.clientSecret`), bound from `NUXT_WCL_CLIENT_ID`, `NUXT_WCL_CLIENT_SECRET`, `NUXT_BLIZZARD_CLIENT_ID` and `NUXT_BLIZZARD_CLIENT_SECRET`. They are never nested under `public`, so they stay out of the browser payload. Both clients also read `process.env` at call time, because on Cloudflare the secrets only arrive with a request. Locally, copy `.env.example` to an untracked `.env` and fill in real values; `.env.example` holds only the bare variable names, with no comments. Before pushing to `main`, the same variables must be set as secrets in the Cloudflare deploy, since a push to `main` deploys straight to production.
